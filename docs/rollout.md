# План внедрения «Сверки» в отделе кадров МФТИ

Исходные условия из ответов заказчика: отдельной ATS нет; вакансии публикуются на hh.ru и на сайте
МФТИ; поток неравномерный, в первые 2–3 дня после публикации бывает 300 и больше откликов в день.
Каналы: hh.ru (основной объём), сайт МФТИ, письма на почту, рекомендации коллег, «Работа в России».
Сейчас первичный скрининг занимает 1–3 минуты на резюме, сопоставление кандидата с несколькими
вакансиями 10–20 минут, оформление перед отправкой заказчику ещё 10–15 минут.

Цифры о качестве и скорости ниже взяты из [README](../README.md) и
[eval/report.md](../eval/report.md). Всё, что помечено «предлагаем», это цели и пороги для
согласования с заказчиком, а не измеренный результат.

## 1. Что меняется для рекрутера и руководителя

| Шаг | Сейчас | С «Сверкой» |
|---|---|---|
| Поступление отклика | рекрутер скачивает резюме с hh, из почты, с сайта | резюме забираются сами из «Входящих» (почта, отклики hh, папка) или загружаются пачкой; повтор по телефону или почте помечается |
| Первичный отсев | 1–3 мин на резюме, просмотр глазами | «Разбор откликов» раскладывает по корзинам: «явно подходят», «нужно ваше решение», «явно не подходят»; решение одной клавишей |
| Сопоставление с вакансиями | 10–20 мин на кандидата | таблица требований по каждой открытой вакансии со статусом и цитатой из резюме, балл с вилкой, рейтинг вакансий, переадресация на более подходящую; на данных кейса около 37 с на резюме при трёх вакансиях |
| Оформление для заказчика | 10–15 мин | «Пакет для заказчика»: один DOCX или PDF со сравнительной таблицей, рисками и вопросами на собеседование; руководитель видит кандидатов без ФИО и отвечает в сервисе |
| Ответ кандидату | вручную | вопросы кандидату по пунктам «не указано», после ответа балл пересчитывается; заготовки писем |

Решение всегда принимает человек:

- автоотказа нет, сервис только раскладывает отклики по корзинам;
- статус «нет» ставится только с цитатой, которая противоречит требованию; если в резюме нет
  данных, это «не указано» и вопрос кандидату;
- спорные случаи (переадресация, широкая вилка, балл у порога) попадают в корзину «нужно ваше
  решение»;
- из корзины «явно не подходят» каждый десятый отклик уходит рекрутеру на выборочную проверку.

## 2. Этапы

| Этап | Что делаем | Кто участвует | Результат |
|---|---|---|---|
| 0. Установка | сервер в контуре МФТИ, `docker compose up -d`, свои ключи и пароли, `RVM_DEMO_LOGIN=0` | ИТ-служба, ответственный за ПДн | сервис открывается из сети МФТИ, демо-вход выключен |
| 1. Пилот, 2–4 недели | 2–3 вакансии с разным профилем, сервис работает параллельно с текущим процессом | 1–2 рекрутера, руководители этих вакансий | цифры из раздела 3, решение о тираже |
| 2. Каналы | почта, hh, сайт; «Работа в России» следующим шагом | ИТ-служба, менеджер МФТИ на hh | отклики приходят без ручного скачивания |
| 3. Тираж | все открытые вакансии | все рекрутеры отдела | сервис в ежедневной работе |
| 4. Развитие | учётки, вход через единую учётную запись МФТИ, обратная связь в hh | ИТ-служба, разработчик | см. ниже |

**Этап 0. Модель.** Сервис работает с любой моделью по OpenAI-совместимому API, вариант
выбирается одной переменной `LLM_BASE_URL`.

- Внешний провайдер по API. В модель уходит только обезличенный текст резюме. Сервер для самого
  сервиса: Docker Compose 2.24 или новее, 2 ГБ памяти, 2 ГБ диска. Стоимость на модели
  `qwen/qwen3.6-35b-a3b` через OpenRouter: около $0,01 на резюме при трёх открытых вакансиях,
  около $3 на пиковый день в 300 откликов; растёт линейно с числом открытых вакансий.
- Локально в контуре МФТИ, данные не покидают машину. Профиль `docker compose --profile local`
  поднимает Ollama; квантованные веса модели 23 ГБ, нужна видеокарта от 32 ГБ, две по 24 ГБ или
  машина с общей памятью от 32 ГБ. Через vLLM или SGLang веса BF16 около 72 ГБ, то есть GPU на
  80 ГБ или несколько меньших. Скорость локального запуска мы не замеряли, это первая задача
  этапа 0 при выборе этого варианта.

**Этап 1. Пилот.** Вакансии берём с разным профилем (например, ИТ, учёт, работа с
образовательными организациями), чтобы увидеть разные типы резюме. Рекрутер ведёт отбор как
раньше и параллельно смотрит разбор в сервисе; в первую неделю по части откликов отмечает время
по-старому, чтобы было с чем сравнивать. Руководители вакансий получают пакеты из сервиса и
отвечают в нём. Раз в неделю короткий разбор: где сервис ошибся, какие строки рекрутер поправил.

**Этап 2. Каналы.**

| Канал | Как подключаем | Что нужно от МФТИ |
|---|---|---|
| Почта отдела кадров | IMAP-ящик: берём непрочитанные письма с вложениями-резюме, вакансию определяем по теме письма | адрес сервера, отдельный ящик или учётка с доступом, пароль только в окружении |
| hh.ru | приложение на dev.hh.ru и OAuth-токен менеджера работодателя; новые отклики по открытым вакансиям забираются с вакансией отклика | регистрация приложения, токен менеджера МФТИ |
| Сайт МФТИ | форма отклика отправляет письмо на ящик выше или кладёт файл в папку `RVM_INBOX_DIR` | доработка формы на стороне сайта |
| «Работа в России» | следующий этап; отклики там тоже доступны только работодателю | доступ работодателя |
| Рекомендации коллег | ручная загрузка или пересылка на ящик | ничего |

**Этап 3. Тираж.** Подключаем все открытые вакансии. Сейчас сервис рассчитан на одну базу
SQLite, одного рекрутера и сотни откликов в день; для нескольких рекрутеров одновременно нужны
учётки из этапа 4.

**Этап 4. Развитие.**

- учётки по людям и вход через единую учётную запись МФТИ вместо двух учёток из окружения;
- закрепление руководителей за их вакансиями: каждый видит только своих кандидатов;
- отметка решений рекрутера обратно в hh (приглашение, отказ), чтобы не дублировать работу;
- шаблоны писем кандидатам, которые отдел правит сам.

## 3. Что меряем на пилоте

Все показатели берутся из журнала событий сервиса и экрана «Сводка», новых вызовов модели для
этого не нужно.

| Показатель | Откуда | Порог успеха (предлагаем) |
|---|---|---|
| Время от отклика до решения рекрутера, медиана | журнал: поступление → решение в «Разборе» | в пиковые дни не больше 1 рабочего дня |
| Доля откликов, разобранных в срок | «Сводка», очередь; срок `RVM_SLA_DAYS`, по умолчанию 2 дня | не меньше 90 % |
| Сколько ждут решения заказчика | «Сводка», медиана «передано → решение заказчика» | фиксируем как базу, порог задаёт заказчик |
| Согласие рекрутера с «не подходит» на выборочной проверке | «Сводка», качество сортировки | не меньше 95 %; ниже — разбираем ошибки до тиража |
| Кандидаты на другую вакансию или в резерв вместо отказа | «Сводка», «Не потеряли» | фиксируем число; цель — больше нуля на каждой вакансии пилота |
| Время рекрутера на одного кандидата | ручная отметка в первую неделю по старому процессу и в сервисе | меньше, чем 10–20 + 10–15 мин по старому процессу |

Тираж начинаем, если заказчик согласен, что пороги достигнуты. Если сортировка расходится с
рекрутером, сначала разбираем строки, которые он поправил, и только потом расширяем поток.

## 4. Персональные данные и 152-ФЗ

Что уже есть:

- до модели текст обезличивается: ФИО, телефоны, почты, ссылки, адреса, дата рождения, возраст,
  пол заменяются масками, перед отправкой повторная проверка; нашли ПДн — не отправляем;
- телефон и почта хранятся как HMAC-хэши, только для пометки повторов;
- исходный файл резюме видит только рекрутер; руководитель видит кандидата без ФИО, ФИО в пакете
  появляется только по решению рекрутера;
- возраст, пол, ФИО и гражданство в оценку и тексты не попадают;
- удаление кандидата стирает все его данные, база удаляет записи с затиранием нулями;
- модель можно держать внутри контура МФТИ (этап 0), тогда данные не покидают машину.

Что нужно до промышленной эксплуатации:

- согласие кандидата на обработку ПДн и отдельно на хранение в резерве: текст для формы на
  сайте, для писем и для откликов с hh;
- срок хранения и автоудаление по нему (сейчас удаление только вручную);
- журнал доступа к ПДн: кто и когда открывал карточку и исходный файл;
- шифрование диска сервера на уровне инфраструктуры МФТИ;
- регламент: кто оператор, кто имеет доступ, как кандидат отзывает согласие, как выбирается и
  оформляется внешний провайдер модели, если он используется.

## 5. Ограничения сейчас

- Разметка качества маленькая: 4 резюме кейса × 3 вакансии, 116 пар требований, разметка наша,
  не организаторов. На ней статусы совпали строго в 72 %, с допустимыми альтернативами в 91 %;
  первое место в рейтинге совпало 4 из 4, порядок вакансий целиком 3 из 4. На пилоте разметку
  нужно расширить на резюме МФТИ.
- Модель путает соседние статусы «частично» и «есть»: на эталоне 7 строк «частично» получили
  «есть», 6 строк «есть» получили «частично». Поэтому статус всегда идёт с цитатой, а решение
  принимает рекрутер.
- «Нет» модель ставит осторожно: точность 100 %, полнота 29 %. Часть настоящих «нет» уходит в
  «частично» или «не указано» и попадает к рекрутеру, а не в отказ.
- Коннектор hh проверен на имитации API по документации hh, на живом API работодателя не
  проверялся: нужен токен менеджера МФТИ.
- Почта на стенде — внутренний демо-ящик, настоящий ящик отдела кадров не подключался.
- Одна учётка на роль (рекрутер и руководитель), одна база SQLite.
- Скорость локальной модели не замерена.

## 6. Риски и что делаем

| Риск | Что делаем |
|---|---|
| Сбой модели или провайдера | отклики остаются во «Входящих» и в базе, ошибка разбора видна в «Сводке»; повторный разбор того же текста берётся из кэша; запасной вариант — второй провайдер или локальная модель, переключение одной переменной `LLM_BASE_URL`; на время сбоя рекрутер работает по-старому |
| Рост потока в пиковые дни | время на пачку пикового дня замеряем на пилоте; при нехватке поднимаем число параллельных разборов `RVM_WORKERS`; очередь и возраст самого старого отклика видны в «Сводке» |
| Ошибки разбора сканов | сканы плохого качества распознаются с предупреждением, цитаты по ним проверяются мягче; такие резюме рекрутер проверяет сам, на пилоте считаем их долю |
| Сопротивление пользователей | пилот идёт параллельно с текущим процессом, ничего не отнимает; решения остаются за рекрутером и руководителем; еженедельный разбор ошибок с рекрутерами; в интерфейсе встроен тур по сценариям |
| Изменения API hh | коннектор hh вынесен в отдельный модуль; ошибка источника не останавливает сервис и видна в статусе «Входящих»; запасной путь — уведомления hh на почту или выгрузка файлов в папку |
